# Golden tests of the UPS model

These files pin down what the model of upst 0.1.2 (`src/model.rs`, `src/status.rs`, `archive::replay`
and `history::{History, Tracker}` as of commit `15f0fb5`, before they moved into upst-core) did: the
event texts, severities and times, estimates, link and outage bookkeeping, recorded history and
replay results. `../golden.rs` runs the same scenarios against upst-core and compares, byte for
byte.

```
scenarios/*.scn         inputs: 7 files, 88 scenarios
expected/*.golden       the output, one per .scn
gen-tracker-window.sh   generates scenarios/51-tracker-window.scn
```

The expected files were generated by a harness on the unmodified upst 0.1.2 code. Since then they
differ from that output only by the deliberate changes below.

## Running

`cargo test -p upst-core --test golden` compares. `UPST_GOLDEN_OUT=<dir>` also writes what it got
there; `UPST_GOLDEN_BLESS=1` overwrites `expected/` with it, for a deliberate change, which then
belongs in the list below.

The live polls of a scenario leave out `EventKind::UpsdBack`, as the upst dashboard does (it logs
its own server-wide "Reconnected to ..." instead); upst 0.1.2 had that event only in replays.

## Deliberate changes since upst 0.1.2

1. **The low battery text takes `battery.charge` as a number** (`flags-lb-charge-raw-text`): the
   event carries `charge: Option<f64>`, so " 19" gives "Battery low (19%)" instead of
   "Battery low ( 19%)", and an empty or non-numeric charge gives "Battery low" instead of
   "Battery low (%)" or "Battery low (n/a%)".
2. **A poll and a lost connection in the same second replay in that order**
   (`replay-poll-and-down-in-the-same-second`, `replay-first-poll-and-down-in-the-same-second`).
   The recorder writes whole seconds, so a poll and the `!down` after it can share a time; the
   replay used to handle the `!down` first and apply the poll after it, ending with the link up and
   an on-line band although upsd was gone. Now a `!down`, `!nodata` or `!start` completes a poll of
   the same second first, and the replay ends down, with "Lost upsd" after the poll's events.
3. **Polls go on after a silence** (`replay-long-silence-without-start`,
   `replay-silence-of-exactly-gap-and-just-over`, `replay-restart-after-long-silence`). A silence of
   more than GAP is still a gap (no data, estimates start over), but a recorder that kept running
   through it, as on a host that slept, writes no `!up` after it; the replay used to ignore every
   later poll until the next `!up`, so an outage after a suspend showed up late or not at all. Now
   the records after the silence are polls again.

The model did not change between `15f0fb5` and `d5e6525`, where upst-core split off. Odd
behaviour 1, 2 and 13 in the list at the end are fixed; the rest still holds.

## Scenario file format

Line oriented; `\r\n` is fine.

* Blank lines, and lines whose first non-blank character is `#`, are skipped
  everywhere (inside poll and journal blocks too).
* On *directive* lines (`===`, `capacity`, `@…`, `replay`, `replay-until`) a
  `#` preceded by whitespace starts a comment. Variable lines and journal
  lines have no inline comments.

| Line | Meaning |
|---|---|
| `=== <name>` | Starts a scenario. Each scenario gets a fresh `Ups::new(0, "localhost", "ups", "", History::new(86400.0, 2.0), capacity)`. Names are unique within a file. |
| `capacity <Wh>` | Optional, before the first step: the `capacity` argument above (`--capacity`). |
| `@<t> poll` | A poll at Unix time `<t>` (f64; integer or decimal). The **full** variable list follows, one `<name> <value>` per line, until the next directive. |
| `@<t> poll+` | Like `poll`, starting from the previous poll's full list in this scenario (empty if none). `<name> <value>` replaces a variable in place or appends it; `-<name>` removes it (an error if it is not there). The runner only ever sees the expanded full list. |
| `@<t> down <why>` | Connection lost: `lost_at(Link::Down(why), t)`. `<why>` is the rest of the line. |
| `@<t> stale <why>` | No data for the UPS: `lost_at(Link::Stale(why), t)`. |
| `@<t> connecting` | `lost_at(Link::Connecting, t)` (the app never does this; it is the only way to get Connecting after a poll). |
| `@<t> gap` | `Ups::gap(t)` (the recorder was not running from `t`). |
| `@<t> estimate` | `Ups::estimate(t)`. |
| `@<t> state` | Prints a state block (see below) for the time range up to `t`. |
| `replay` | The following lines are journal lines (the `src/journal.rs` format: `<t> !start`, `<t> !up`, `<t> !tick`, `<t> !down <why>`, `<t> !nodata <why>`, `<t> <name> <value>`, `<t> -<name>`) up to … |
| `replay-until <t>` | … this line, which runs `archive::replay(&mut ups, &records, t)` on the scenario's `Ups` (fresh, unless steps came before it). Every journal line must parse with `journal::Record::parse`; records are passed in file order (no clamping as `journal::for_each` does). |

Variable lines: the name is everything up to the first space, the value is
the rest of the line, verbatim (it may contain spaces). `name` alone gives an
empty value. Leading blanks of the line are ignored. A value wrapped in
double quotes is taken without the quotes, to keep blanks an editor would
strip (`ups.alarm "   "`, `battery.charge " 42 "`). The order of the list is
kept (`poll+` keeps the base order and appends), although the old `apply`
does not depend on it. A name listed twice in a `poll` is an error.

Steps run in file order. Times may go backwards between steps (one scenario
estimates at a time before the discharge started), but **no two polls of one
scenario may share a time**, including a replayed poll and a live one: the
runner panics, because the old `apply` finds this poll's changes by comparing
`Instant`s derived from the poll time, and equal times would make that
depend on clock jitter.

## Output format, and the old API behind each line

Scenarios are printed in file order and separated by one empty line. Times
(`<t>`) print as an integer when whole, else with `{:.3}`. Optional numbers
print as `None` or with `{:.3}`.

### Steps

| Output | Produced by |
|---|---|
| `=== <name>` | the scenario name |
| `capacity <c>` | `Scenario::capacity`, f64 `Display`; only when given |
| `@<t> poll <n> vars` | before `ups.apply(vars, from_unix(t))`; `n` = length of the full list |
| `  <t> <Severity:?> <text>` after a poll | each `(Severity, String)` `apply` returned, in order; `t` is the poll's time |
| `@<t> down <why>` / `@<t> stale <why>` / `@<t> connecting` | before `ups.lost_at(link, from_unix(t))` |
| `  <t> <Severity:?> <text>` after those | the `Some((Severity, String))` `lost_at` returned (nothing for `None`) |
| `@<t> gap` | `ups.gap(from_unix(t))`; no other output |
| `@<t> estimate` then `  estimate …` | `ups.estimate(t)`, formatted as below |
| `@<until> replay-until <n> records` | before `archive::replay(&mut ups, &records, until)`; `n` = number of journal lines |
| `  <t> <Severity:?> <text>` after a replay | each `(f64, Severity, String)` `replay` returned; `t` is the time it returned |
| `@<t> state` | followed by a state block with `t1 = t` |
| `--- end` | after the last step; followed by the final state block with `t1` = the scenario's latest time |

Estimate line (`Ups::estimate` → `Option<Estimate>`):

```
estimate None
estimate trend=<Trend:?> per_hour=<{:.6}> rough=<bool> to_low=<opt> to_empty=<opt> to_full=<opt> watts=<opt>
```

### State block

`t0` is the scenario's earliest time (any step time, any journal record
time, any `replay-until`), `t1` the latest one (or the `@<t> state` time).

```
state link=<Link:?> outages=<n> battery_secs=<{:.3}> outage_start=<t|None> power_since=(<t>, <bool>)|None since=<t|None> polls=<n> headline=<"…":?> power=<Power:?> capacity_wh=<Option<f64>:?> capacity_guessed=<bool>
status tokens=<[…]:?> severity=<Severity:?> trend=<Option<Trend>:?> updated=<{:.1}|None>
var <name> <value:?>                                  (one per variable)
changed <name> prev=<Option<String>:?> at=<{:.1}>     (one per variable whose `changed` is Some)
bands <t0>..<t1> <Band:?>,<Band:?>,…                  (20 columns)
series <name> <t>:<v> <t>:<v> …                       (one per history series)
charge_at <t>=<v|None> … (5 times)                    (only if a battery.charge series exists)
now=<t1> estimate …
```

| Field | Old API |
|---|---|
| `link`, `outages`, `battery_secs`, `polls`, `capacity_wh`, `capacity_guessed` | the `Ups` fields of the same name |
| `outage_start`, `since` | `Ups::outage_start` / `Ups::since` through `model::unix` |
| `power_since` | `Ups::power_since` (`(SystemTime, bool)`), time through `model::unix` |
| `headline` | `ups.status.headline().0`, Debug-quoted |
| `power` | `ups.status.power()` |
| `tokens` | `ups.status.tokens()` (Debug of `&[String]`) |
| `severity` | `ups.status.severity()` |
| `trend` | `ups.tracker.trend()` |
| `updated` | `Ups::updated` (an `Instant`), mapped back to Unix time, `{:.1}` |
| `var` | every entry of `ups.vars` (BTreeMap order), `Var::value` Debug-quoted |
| `changed … prev= at=` | `Var::prev` (Debug) and `Var::changed` (an `Instant`) mapped back to Unix time, `{:.1}` |
| `bands` | `ups.history.band_columns(t0, t1, 20, t1)` |
| `series` | `ups.history.names()` sorted; for each, every point of `history.get(name).window(-inf, +inf)`; `v` with f64 `Display` |
| `charge_at` | `history.get("battery.charge").at(t)` at `t0 + (t1 - t0) * k / 4`, k = 0..=4 |
| `now=<t1> estimate …` | `ups.estimate(t1)` |

The old model keeps `Var::changed` and `Ups::updated` as `Instant`s made by
`model::instant(at)` = `Instant::now() - (SystemTime::now() - at)`. The
runner maps them back with `SystemTime::now() - (Instant::now() - i)` and
prints them to 0.1 s; the error is a few microseconds (a 50 ms scheduling
hiccup between two clock reads would be needed to flip a digit). After every
live poll it asserts that `updated` maps back to the poll time within 0.05 s,
so a platform where `instant()` cannot reach 2023 (it then falls back to
`now`) fails loudly instead of printing garbage. A new API that stores wall
time should print the stored time with `{:.1}`.

## Determinism

* All times are fixed (around 1 700 000 000, Nov 2023). The runner never
  calls `Ups::lost`, `power_age`, `battery_total` or anything else that reads
  the wall clock; the only wall-clock use is the `Instant` mapping above.
* `HashMap` iteration (`History::names`) is sorted; everything else iterates
  BTreeMaps or Vecs.
* Two consecutive runs gave byte-identical output (same sha256 for all 7
  files), and a compare run against `expected/` passed. A deliberately edited
  expected file made the compare run fail with the right line.

## Odd behaviour of upst 0.1.2 the goldens pin down

Found while writing the scenarios. Those marked fixed are deliberate changes (see above); the
goldens keep the rest, and fixing one means regenerating the affected scenario on
purpose.

1. **Fixed: poll and `!down` in the same second** (`replay-poll-and-down-in-the-same-second`,
   `replay-first-poll-and-down-in-the-same-second`). `replay` applies a poll
   only when a record with a *different* time arrives, but handles `!down` /
   `!nodata` at once. A journal ending `60 battery.charge 99` / `60 !down …`
   replays as "Lost upsd" and then the poll, so the replay ends with
   `link=Up` and an Online band. On a fresh Ups this gives "Cannot reach
   upsd" followed by "Running on battery" at the same second, link Up. The
   recorder floors times to whole seconds, so this is reachable with poll
   intervals under a second apart from the failure.
2. **Fixed: a silence over GAP without `!start`** (`replay-long-silence-without-start`,
   `replay-silence-of-exactly-gap-and-just-over`). After the gap `up` is
   false and only a `!up` sets it again. A recorder that kept running (host
   suspended and resumed) still has feed Up and writes no `!up`, so every
   later set and tick is ignored until the next down/up cycle or restart: the
   OB at 1000 is reported at the `!up` at 1200, a `!down` in between gives no
   "Lost upsd" (Down("not recorded") → Down is silent) but the `!up` gives
   "Reconnected to localhost".
3. **Replay after a live `lost()`** (`replay-after-a-live-stale`,
   `replay-after-a-live-down`). The app applies NoData/Down to a Ups at once
   even while its polls are held for recorded history. The replay's first
   poll then logs "UPS data is fresh again (was: …)" at the first recorded
   time, before the "No data" event it answers; the band deque gets the live
   NoData entry first and older entries after it (not sorted by time, which
   `band_columns`' `partition_point` and `trim` assume); for Down the log
   shows "Cannot reach upsd" and then "Lost upsd" (the app re-applies the
   live Down after the replay, emulated by the second `down` step).
4. **First poll already on battery** (`power-first-poll-on-battery*`): not
   counted in `outages` (stays 0) but its time is added to `battery_secs`
   when power returns.
5. **ups.status missing or empty during an outage** (`power-ob-to-no-status`):
   "Left battery power after 30s on battery" (Good), and OB coming back
   counts as a second outage.
6. **Unrecorded time counts as battery time** (`replay-gap-during-an-outage`:
   "Power restored after 32m 20s" across a 31 min gap; `link-gap-then-poll`).
7. **Link Down → Stale is silent** (`link-down-to-stale`), yet the next poll
   says "UPS data is fresh again (was: …)" with no "No data" before it.
   Connecting → Stale → Down says "Lost upsd" although nothing was ever
   reached (`link-connecting-stale-then-down`), and a Stale before the very
   first poll makes that first poll report fresh data
   (`link-connecting-stale-first`).
8. **Duplicate status tokens give duplicate events** (`OL XYZ XYZ` → two
   "Status flag XYZ set"); lowercase `ol` is an unknown flag and power
   Unknown (`flags-duplicate-lowercase-and-spacing`).
9. **Fixed: the LB text quoted battery.charge raw**: "Battery low ( 19%)",
   "Battery low (%)", "Battery low (n/a%)" (`flags-lb-charge-raw-text`).
10. **FSD, TRIM and BOOST** have a set event but no clear event; TEST, CHRG,
    DISCHRG, COMM and OL never have events (`flags-*`). Probably intended.
11. **ups.alarm / ups.test.result fire again** when the variable disappears
    and comes back with the same text (`alarm-reappears-with-the-same-text`,
    `test-result-changes`).
12. **Tracker**: a rise in charge while discharging is kept as a step (no
    reset), so the 12-step window can straddle it (`estimate-wrong-direction`);
    an estimate for a time before the segment started uses `(now - t0).max(1)`
    and gives −3600 %/h (last estimate of `estimate-single-step-rough`; never
    happens live). Dropping the oldest 32 of more than 64 steps cannot be
    observed through `rate()` (it only reads the last 12), so no golden pins
    it.
13. **Fixed: latent nondeterminism in `apply`**: "changed during this poll" is
    `Var::changed == Some(mono)` where `mono = instant(now)`. Two polls with
    the same wall time get Instants that are equal or not depending on clock
    jitter, so an alarm or self-test event could fire twice or not. `replay`
    never applies two polls at one time and the harness forbids it, but a
    wall clock stepping back live could hit it. `instant()` also maps any
    future time to `Instant::now()`.
